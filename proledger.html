How it is built

Managed backend. Deliberate client logic.

01 / INTERFACEReact application

Onboarding, ledger views, currency formatting, imports, exports, and receipt review.

02 / IDENTITY + SYNCSupabase Auth & cache

Email/Google sign-in, user-scoped local data, pending writes, and cloud refresh logic.

03 / PERSISTENCEPostgreSQL storage

Serialized ledger values keyed by user and storage key, with row-level policies defined in SQL.

Receipt recognition runs in a browser worker. Capacitor projects reuse the web UI for native builds, with separate native authentication callback handling.

Engineering detail

Protecting account boundaries.

Cloud requests may finish after the signed-in account changes. The storage layer checks the active user scope around asynchronous operations, and isolates cached data and pending writes by user.

Local tests exercise an in-flight read during an account switch, so old results do not populate the next account’s cache.

Tradeoff

Simple persistence, careful synchronization.

Storing serialized ledger values makes persistence and migrations compact. It also limits database-side transaction queries and requires care when multiple devices update the same ledger.

This is a managed Supabase backend, with an account-deletion Edge Function—not a custom banking platform.

Evidence & current scope

Tested locally. Claims kept specific.

On October 9, 2026, all 30 offline tests passed, covering currency precision, onboarding, numeric limits, receipt parsing, native authentication callbacks, and storage isolation.

The public sign-in page and local source were reviewed. Live database policies, authenticated production workflows, account deletion, app-store releases, and production-scale behavior were not verified. Native project files demonstrate implementation work, not a published mobile release.
